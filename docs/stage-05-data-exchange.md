# Этап 5: безопасный локальный импорт и резервное копирование

Проверено 8 октября 2026 года. Приложение 1.4.0 (`versionCode = 5`), Room 5, экспорт JSON 4. Основной этап реализован для документированных форматов. Адаптер неизвестной фактической выгрузки скалолазания отложен до получения обезличенного образца; совместимость с реальной многолетней историей не объявляется проверенной.

## Реализовано

- UUID профилей и сохранённые сопоставления источников добавлены миграцией `4 → 5`. Схемы 2/3/4 не менялись; схема 5 экспортирована с identity hash `1da88f247203165323b8d28b7115fa9e`. Признак неиспользованного начального центра применяется только к новым справочникам; миграция не угадывает его по названию старого центра.
- JSON 4 переносит UUID и времена создания, профили, центр/спорт, футбольные поля, трассы и их метаданные/исторические повторы, серии, статусы и связь плана с серией, избранное и сопоставления. Общие записи и спортивные детали остаются раздельными.
- `ImportParser`, `BackupValidation`, `DataExchange` заменяют прежнее слияние по содержимому. Предпросмотр — только чтение; применение повторно проверяется и выполняется в одной транзакции. Подмена чужого UUID трассы, конфликт родителя, неизвестный статус/частота/спорт, некорректная дата/число/категория или ссылка не приводят к частичной записи.
- Две одинаковые реальные тренировки с разными UUID сохраняются. Повторный UUID пропускается; разные данные того же UUID требуют явного сохранения локальной записи без перезаписи. Возможное совпадение содержания — только подсказка с отдельным явным пропуском.
- Несколько профилей из файла требуют выбора одного или сохранения всех отдельно. Личная статистика/календарь не смешивают отдельные профили. Ранее явно объединённые профили не объявляются автоматически разделимыми.
- Для CSV центр требует подтверждения даже при совпадении старого номера с локальным ID. Можно сопоставить существующий центр или создать исторический; последующие подтверждённые сопоставления сохраняются в копии. Реальный пользовательский центр не перезаписывается импортом.
- JSON 1–3 адаптируется явно. Старые обозначения скалолазания, результаты, число попыток и несколько трасс в одной тренировке сохраняются. Отсутствующие старые владельцы, даты создания и связи плана с серией не угадываются. Идентичность старого файла зависит от SHA-256 точных байтов и позиции, а не спортивного содержания.
- Футбольный CSV: UTF-8/BOM и Windows-1251, `;`/`,`, кавычки и переносы внутри них, физические номера строк, десятичная запятая; необязательные дистанция, игроки и минуты. JSON требует корректного UTF-8 и не маскирует повреждение сменой кодировки.
- Общая дата/повторение и спортивные валидаторы используются ручным вводом и импортом. Новые тренировки/планы требуют текущей доступности спорта в центре; восстановление истории не возвращает удалённый из центра спорт и допускает исторический центр без текущих видов спорта.
- SAF `OpenDocument`/`CreateDocument`, согласованный снимок перед диалогом, фоновое чтение/разбор, лимиты 16 МиБ/100000 объектов, блокировка повторных файловых операций, сохранение ViewModel при повороте. После записи копия закрывается, читается обратно и сравнивается по байтам. Отмена не показывает успех; отказ сообщает о возможном неполном файле.
- Обе пользовательские инструкции обновлены по навыку `bilingual-manual-commit`; формат отдельно описан в `backup-format.md`, проверяемый синтетический JSON включён в Android test assets. Приложению не добавлялись сеть, внешние аккаунты, широкие разрешения на хранилище или автоматический бэкап.

```powershell

.\gradlew.bat --offline verifyOfflinePolicy testDebugUnitTest lintDebug assembleDebug assembleRelease connectedDebugAndroidTest --warning-mode all
```

Финальный результат: `BUILD SUCCESSFUL`; 35 unit-тестов и 47 Android-тестов, 0 failures/errors/skipped; Lint — `No issues found`; debug и unsigned release APK собраны, офлайн-политика проверена для обеих сборок. Предупреждения Gradle `Configuration.setVisible` и Protobuf `sun.misc.Unsafe` относятся к сборочным инструментам и остаются неблокирующими.

Проверены полное восстановление допустимого контрольного набора со всеми текущими связями и временами, неизменённый повторный импорт, JSON 1/2/3/4, сохранение одинаковых реальных тренировок, явный пропуск/конфликт, несколько владельцев CSV/JSON, центр с неизвестным номером, перенос сопоставлений через новый бэкап, несовместимый UUID трассы, ошибочные ссылки/статусы/частоты и дата, смена базы после предпросмотра, отключённый у центра спорт. SQL trigger имитирует отказ на второй вставке: все изменения, включая новый центр и идентичность профиля, откатываются. Эквивалентные ISO-обозначения одного времени не создают ложного конфликта UUID.

Compose-тесты проверяют недоступность применения при ошибках, отмену, выбор профиля, явное сохранение локального конфликта и включение возможного совпадения по умолчанию. Файловые тесты проверяют усечение существующего файла, обратное чтение, ошибку провайдера, отмену диалога и снятие блокировки после успеха/отказа экспорта. Миграции проверены с `4 → 5` и всей цепочкой `1 → 5`; UUID профилей сохраняются при повторном открытии.

## Ограничения и следующий этап

Реальные исторические файлы и подтверждение применимости шкал к конкретным залам отсутствуют. Для неизвестного формата скалолазания нужен образец; известные JSON переносят группировку трасс. Старые утраченные связи и владельцы нельзя восстановить. При объединении текущие пользовательские метаданные центра/профиля остаются локальными, история не заменяет базу целиком. Другие профили сохраняются в файле, но UI переключения пока нет. Повреждённая/неподдерживаемая старая база экспортируется без удаления payload, однако строгий импорт такого файла может отказать.

API 26, физическое устройство, стресс-прогоны многолетней истории, большое системное увеличение шрифта и восстановление черновиков после смерти процесса остаются этапу 11/соответствующим UI-этапам. Снимок/предпросмотр при обычном повороте проверен; закрытый процесс требует начать файловую операцию заново. Исключения серий и связь плана с результатом появятся на этапе 8 и должны одновременно расширить формат бэкапа. Следующий этап — 6, справочник центров и архивирование без потери истории; любое новое хранимое свойство также требует поддержки обмена.
