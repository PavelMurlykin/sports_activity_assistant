# Контракт спортивного модуля

Общая запись `TrainingEntity` хранит дату, локальный профиль, вид спорта, центр, время создания и UUID. Спортивные показатели остаются в дочерних таблицах. Сохранение общей записи и деталей выполняется в одной транзакции Room. `SportModule` содержит проверку показателей, запись дочерних сущностей, кодек спортивной части JSON, подробности для карточки и расчёт агрегатов.

Регистрация бизнес-модулей — `data/sport/SportModules`. Регистрация Compose-редактора и оформления — `ui/components/SportEditors`. Общий диалог, календарь и статистические экраны не выбирают реализацию через `when(sport.slug)`. Неизвестный модуль нельзя записать или импортировать; исторические записи такого спорта сохраняются и отображаются с предупреждением. Экспорт сохраняет все имеющиеся спортивные части, в том числе несогласованные старые данные; это не означает, что их повторный импорт пройдёт новые проверки.

Для добавления спорта:

1. Определить дочерние сущности и типизированный ввод показателей; расширить DTO ввода и версионируемый формат обмена. Универсальные поля тренировки не изменять.
2. Создать `SportModule`, проверяющий ровно свою спортивную часть и отклоняющий чужие детали. Реализовать сохранение, обмен, карточку, показатели и краткую сводку.
3. Добавить модуль в `SportModules.all` и соответствующий `SportEditor` в `SportEditors`. `LocalSeed` добавит отсутствующую запись справочника по slug, сохранив существующие числовые ID.
4. Добавить таблицы/отношения в Room, увеличить версию схемы, экспортировать её и написать миграцию без destructive fallback. Никогда не менять старые сохранённые схемы под новые сущности.
5. Проверить валидатор и кодек модульными тестами, формы Compose-тестами, миграцию и транзакционное сохранение Android-тестами. Проверка `everySupportedSportHasAnEditor` должна проходить. Не включать незавершённый модуль в рабочий реестр.

UUID хранятся в базе и не меняются при редактировании центра; JSON 4 переносит их вместе с датами создания и связями. Спортивный кодек должен сохранять идентичность дочерних сущностей: `ClimbingRouteInput.publicId` и `ClimbingRouteBackup.publicId` участвуют в восстановлении, новый ручной ввод без UUID получает новый идентификатор. Общие дата/повторение проверяются `TrainingValidation`, спортивные показатели — `SportModule.validate(input, allowHistorical = false)`; импорт передаёт `allowHistorical = true` только для явно сохранённой неоднозначной истории, не ослабляя проверки современных категорий. Исторический адаптер не должен зависеть от изменяемого будущего справочника. Сохранение черновика формы при пересоздании экрана дорабатывается на этапе 7.

`ImportParser` адаптирует документированные JSON 1–3 и футбольный CSV к модели обмена, `BackupValidation` проверяет весь файл, `DataExchange` строит предпросмотр и повторно проверяет применение в транзакции. Нельзя возвращать молчаливый пропуск неизвестной ссылки или дедупликацию по одному содержимому. Любая новая хранимая сущность/свойство должна одновременно получить поддержку в версионируемом бэкапе и тесте восстановления; старые приложения отклоняют неизвестные версии. Подробности — в `backup-format.md`.
