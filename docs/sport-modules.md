# Контракт спортивного модуля

Общая запись `TrainingEntity` хранит дату, локальный профиль, вид спорта, центр, время создания и UUID. Спортивные показатели остаются в дочерних таблицах. Сохранение общей записи и деталей выполняется в одной транзакции Room. `SportModule` содержит проверку показателей, запись дочерних сущностей, кодек спортивной части JSON, подробности для карточки и расчёт агрегатов.

Регистрация бизнес-модулей — `data/sport/SportModules`. Регистрация Compose-редактора и оформления — `ui/components/SportEditors`. Общий диалог, календарь и статистические экраны не выбирают реализацию через `when(sport.slug)`. Неизвестный модуль нельзя записать или импортировать; исторические записи такого спорта сохраняются и отображаются с предупреждением. Экспорт сохраняет все имеющиеся спортивные части, в том числе несогласованные старые данные; это не означает, что их повторный импорт пройдёт новые проверки.

Для добавления спорта:

1. Определить дочерние сущности и типизированный ввод показателей; расширить DTO ввода и версионируемый формат обмена. Универсальные поля тренировки не изменять.
2. Создать `SportModule`, проверяющий ровно свою спортивную часть и отклоняющий чужие детали. Реализовать вставку и атомарное обновление деталей, обмен, карточку, показатели и краткую сводку. `updateDetails` должен сохранять ID/UUID остающихся дочерних сущностей; `validateEdit` отделяет допустимое исправление истории от создания новых неоднозначных данных.
3. Добавить модуль в `SportModules.all` и соответствующий `SportEditor` в `SportEditors`. `LocalSeed` добавит отсутствующую запись справочника по slug, сохранив существующие числовые ID.
4. Добавить таблицы/отношения в Room, увеличить версию схемы, экспортировать её и написать миграцию без destructive fallback. Никогда не менять старые сохранённые схемы под новые сущности.
5. Проверить валидатор и кодек модульными тестами, формы Compose-тестами, миграцию и транзакционное сохранение Android-тестами. Проверка `everySupportedSportHasAnEditor` должна проходить. Не включать незавершённый модуль в рабочий реестр.

UUID хранятся в базе и не меняются при редактировании центра, тренировки и остающихся трасс; JSON 6 переносит их вместе с датами создания и связями. Состояние архива центра переносится вместе с идентичностью; новая ручная запись/план требует активного центра с выбранным спортом, восстановление истории не требует текущей доступности. План/вхождение связывается с общим результатом без зависимости от спортивных полей; завершение выполняется вместе с дочерними деталями в одной транзакции. Исключения серий и ссылки переносятся в JSON 6.

Нормализация `CenterNames` используется и в ручном редакторе, и в сопоставлении импорта.

Спортивный кодек должен сохранять идентичность дочерних сущностей: `ClimbingRouteInput.publicId` и `ClimbingRouteBackup.publicId` участвуют в восстановлении, новый ручной ввод без UUID получает новый идентификатор. Общие дата/повторение проверяются `TrainingValidation`, спортивные показатели — `SportModule.validate(input, allowHistorical = false)`; импорт передаёт `allowHistorical = true` только для явно сохранённой неоднозначной истории, не ослабляя проверки современных категорий. Исторический адаптер не должен зависеть от изменяемого будущего справочника. `SportEditor.rememberDraft(initial)` получает типизированную исходную запись; его Compose-состояние должно быть saveable, включая весь список дочерних строк и их UUID. `SportDraft.Content(enabled)` блокирует поля на время записи. Общая форма использует отдельный saveable-контейнер каждого спорта. `TrainingValidation.completedDate` ограничивает новые ручные результаты сегодняшним днём; импорт сохраняет исторические даты, а редактор позволяет оставить исходную будущую дату или исправить её на прошлую. Числовые спортивные правила одинаковы при ручном вводе и импорте.

`ImportParser` адаптирует документированные JSON 1–3 и футбольный CSV к модели обмена, `BackupValidation` проверяет весь файл, `DataExchange` строит предпросмотр и повторно проверяет применение в транзакции. Нельзя возвращать молчаливый пропуск неизвестной ссылки или дедупликацию по одному содержимому. Любая новая хранимая сущность/свойство должна одновременно получить поддержку в версионируемом бэкапе и тесте восстановления; старые приложения отклоняют неизвестные версии. Подробности — в `backup-format.md`.

Этап 7: `TrainingEditSnapshot` хранит исходные показатели и каноническую ревизию. Проверка владельца, сверка ревизии, изменение родительской записи и деталей выполняются в одной транзакции. Ревизия исключает названия справочников, поэтому переименование центра не конфликтует с исправлением результата. Спорт при редактировании неизменяемый. Старая ссылка на закрытый центр может остаться; новое назначение проверяется по актуальной доступности. Удаление каскадирует только спортивные детали. Повторный запрос создания после восстановления процесса использует UUID формы как UUID тренировки; повторные изменения/удаление уже применённого результата не создают дублей. Работа записи живёт в ViewModel независимо от ожидающей композиции, а UI хранит saveable-признак незавершённого подтверждения.

Этап 9: `SportModule.aggregate(dao, StatisticsSelection, includeMetrics)` реализует SQL-агрегаты и возвращает `SportAggregate` (подробные показатели/краткая сводка). Общий репозиторий передаёт одну выборку — текущий профиль, ID спорта, включительные даты и необязательный ID центра — и держит читающую транзакцию для согласованного снимка. Для обзора `includeMetrics = false` позволяет не считать ненужные подробности. Все новые запросы модуля должны повторять эти предикаты, учитывать только результаты и сохранять отличие null от 0. Целочисленные суммы — Long. Текстовые дистанции BigDecimal суммируются точными порциями по 512 значений, без SQLite REAL. Методы `metrics(items)`/`highlights(items)` остаются контрольным расчётом для тестов с тем же форматированием, не способом загрузки всей истории в UI.

Общий обзор использует SQL-группировки по спорту/месяцу и ленивую выдачу пустых месячных карточек. История использует `observeTrainingPage` / 20 записей, порядок date DESC, id DESC, count и страницу из одной транзакции. При изменениях Room страница строится заново, а не дописывается к старому списку. `observeTrainingsForSport` теперь возвращает только первую ограниченную страницу; для всей истории используйте постраничный API, а полный снимок оставьте экспорту. Наблюдение календаря использует invalidation tracker и запрашивает детали только видимого диапазона вместо загрузки всех тренировок как сигнала изменения. Смена фильтра отменяет прежний Flow; UI не показывает результат с другой выборкой. Применённый фильтр переносится через SavedStateHandle, черновик формы — через rememberSaveable.
