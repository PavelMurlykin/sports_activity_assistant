# Этап 3: локальная модель и спортивные модули

Дата: 7 октября 2026 года. Предыдущий отправленный этап: `6931cd9`.

## Реализовано

- Схема Room 3; экспорт неизменной предшествующей схемы 2 и новой схемы 3 в `app/schemas`. Версия APK — `1.2.0`, код 3; формат JSON отдельно остаётся версии 2.
- Профиль содержит только локальный ID, необязательное имя и время создания. Внешние ID и поля внешнего аккаунта удаляются миграцией, без замены локальных ключей. Существующие имена из старых полей имени/фамилии сохраняются; профили не объединяются.
- Тренировки, центры, трассы, планы и серии имеют UUID с уникальным индексом в своей таблице. Редактирование центра сохраняет UUID и время создания. Две одинаковые вручную записанные тренировки одного дня не объединяются.
- `LocalSeed` работает транзакционно, дополняет отсутствующие виды спорта по slug, не заменяет существующие ID и записи. Репозиторий ждёт инициализации перед потоками и операциями. Фоновой гонки первичного заполнения и константы ID профиля в ViewModel больше нет. Демонстрационные результаты находятся только в `androidTest`.
- `SportModule` объединяет валидатор, сохранение дочерних данных, спортивный кодек, карточку и расчёт статистики. `SportEditors` регистрирует форму и оформление. Общие сценарии не содержат ветвления `when(sport.slug)`.
- Ручной ввод и импорт используют один валидатор спортивной части. Нельзя сохранить футбольную тренировку с трассами или скалолазание с футбольными данными. Ошибка не оставляет общую запись без деталей. Неизвестная дисциплина и недопустимое число повторов не подменяются значениями по умолчанию при импорте.
- Неизвестный спорт явно отклоняется при новой записи и импорте. Исторические записи такого спорта сохраняются, отображают общие сведения с предупреждением. Экспорт не отбрасывает уже сохранённые спортивные части, даже если старый импорт создал несогласованные детали.
- Для родительских сущностей убран `REPLACE`, способный удалить дочерние данные при конфликте. Обновление центра выполняется через `UPDATE`.

## Миграция без потери связей

Перед изменениями проверяются внешние ключи. Таблицы, зависящие от профиля, копируются во временные таблицы без FK. Затем рабочие таблицы удаляются от дочерних к родительской; профиль создаётся без внешних полей, остальные таблицы и индексы восстанавливаются из DDL предшествующей базы. Данные копируются с прежними ключами, количества и статусы не меняются. UUID заполняются до создания уникальных индексов. Сохраняются high-water marks `sqlite_sequence`, включая ID удалённых записей. После проверки FK временные копии удаляются. Room выполняет миграцию в транзакции и валидирует итоговую схему; destructive fallback отсутствует.

Принципы экспорта схем и проверки миграций: [документация Room](https://developer.android.com/training/data-storage/room/migrating-db-versions), API применённого Room 2.x: [MigrationTestHelper](https://developer.android.com/reference/androidx/room/testing/MigrationTestHelper). Compose-тесты используют новый входной API из уже выбранной библиотеки: [руководство v2](https://developer.android.com/develop/ui/compose/testing/migrate-v2); дополнительных alpha-зависимостей не добавлено.
