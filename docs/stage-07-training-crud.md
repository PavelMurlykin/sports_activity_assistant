# Этап 7 — ввод и управление результатами тренировок

Завершён 8 октября 2026 года. Приложение 1.6.0 (versionCode 7), Room 6, JSON 5. Формат обмена, таблицы, старые схемы Room и версии библиотек не менялись.

## Реализовано

- Создание, просмотр, исправление и подтверждаемое удаление результатов из календаря и списка конкретного спорта.
- Общие дата/центр и спортивные детали сохраняются одной транзакцией. UUID, первоначальное время создания и числовой ID тренировки сохраняются. Остающиеся трассы обновляются без замены их ID/UUID; новые получают новые UUID.
- Спорт сохранённого результата неизменяемый. Прежний центр может остаться архивным/без текущего предложения спорта; новый центр должен быть активным и предлагать этот спорт.
- Четыре обязательных футбольных значения допускают ноль, пустые три необязательных остаются null. Числовые клавиатуры, десятичная точка/запятая, ошибки у полей, ограничения длины/точности и общие с импортом бизнес-правила.
- Добавление, изменение и удаление нескольких трасс с раздельными шкалами и результатами. Должна остаться хотя бы одна строка. Число попыток положительное: все попытки строки имеют один результат; разные результаты записываются отдельно.
- Исторические исходные дисциплина/категория сохраняются только для чтения. Результат и repeatCount можно исправить, строку удалить, современную добавить. Неоднозначная старая категория не получает подтверждённую шкалу автоматически.
- Поле YYYY-MM-DD и календарный выбор даты. Новый ручной результат не может быть будущим; для него нужен план. Импорт не теряет исторические будущие даты: редактор позволяет оставить первоначальную или исправить на сегодня/прошлое.
- Ошибка записи остаётся в форме с введёнными данными. При записи заблокированы поля, повторное подтверждение и отмена. Кнопки формы результата располагаются над системной клавиатурой.
- Saveable-черновики даты, центра, всех полей и всех трасс/UUID/повторов; отдельный черновик для каждого спорта. Вложенное создание центра хранится на уровне основной формы. Начальный пустой снимок загружаемого справочника не сбрасывает восстановленный центр.
- Запись живёт в ViewModel независимо от ожидающей композиции. UUID формы используется как UUID нового результата: повторное подтверждение после восстановления процесса не создаёт дубль. Повтор уже применённого изменения/удаления безопасен.
- Ревизия исходной тренировки проверяется в транзакции вместе с владельцем. Устаревшие изменения и удаления отклоняются; переименование центра не вызывает ложный конфликт.
- После успешного CRUD обновляются календарь и наблюдаемые статистические потоки. Отменяется предыдущий асинхронный запрос календаря, чтобы устаревший ответ не перекрыл новый.

SportModule получил validateEdit и updateDetails; SportEditor — исходные данные и блокируемый Content. Общая форма не ветвится по slug спорта. Контракт расширения обновлён в sport-modules.md.

Новые проверки: все числовые поля и будущая дата; идентичность после исправления; обновление календаря/агрегатов/копии; null необязательных; сохранение ID/UUID трасс; каскадное удаление без удаления планов/центра; чужой профиль и устаревшая ревизия; ошибка SQL после обновления/удаления трасс с полным откатом; закрытый исторический центр; импорт будущей истории; одновременный повтор с одним UUID; сохранение неизвестной исторической дисциплины и повторов; ошибку можно исправить; повторное нажатие; отмена; календарный выбор; переключение спорта; восстановление нескольких трасс и вложенного центра; загрузка справочников.

В первых прогонах найдены и исправлены потеря вложенного черновика и перекрытие кнопок клавиатурой. Для функциональной проверки кнопок после анимации IME применяются семантические действия: меняющиеся во время анимации экранные координаты приводили к нестабильному тестовому нажатию. Обычные нажатия отдельно проверены на установленном приложении. Официальный StateRestorationTester пока использует исходный ComposeContentTestRule; остальные прежние тесты остаются на v2.

Неблокирующие предупреждения инструментов: устаревающий Configuration.setVisible (Gradle 11) и sun.misc.Unsafe библиотеки Protobuf под JDK 25. Ошибок компиляции, замечаний Lint и падений финальных тестов нет.

## Локальные сценарии

Проверки выполнялись через установленный APK в авиарежиме (airplane_mode_on = 1), без пользовательских исторических файлов.

1. Футбол: введено 5 забитых, остальные обязательные нули, необязательные пустые. Форма сохранена после поворота и фактического завершения фонового процесса: PID 6134 → 6412, холодный запуск, значение 5 осталось.
2. Обновление промежуточного APK поверх синтетической записи сохранило её. В статистике показано 5:0; редактированием личные голы изменены на 2. Сохранение нажато при открытой числовой клавиатуре, кнопки не перекрыты; итоги и карточка обновлены.
3. Отмена подтверждения удаления оставила результат. Подтверждение удалило только созданную тестовую тренировку: игры/голы стали нулевыми, выбранный день календаря пуст.
4. Скалолазание: трудность 6a успешно и болдер 6A с тремя неуспешными попытками в одной тренировке. Поворот и реальное завершение фонового процесса (PID 6554 → 7219) сохранили обе строки, шкалу Fontainebleau, число 3 и результат. После сохранения — одна тренировка, четыре попытки, одна успешная (25%), максимум трудности 6a; болдер не учитывается в успешном максимуме.
5. После последнего полного прогона итоговый APK вновь установлен и запущен: versionName 1.6.0 / versionCode 7, авиарежим включён. Instrumentation удаляет тестовую установку, поэтому контрольный запуск чистый, без демонстрационной истории.

Снимки ручной проверки находятся только в игнорируемой .local-testing, в Git не включены. Синтетические тестовые записи не входят в инициализацию приложения.
