# Sports Activity Assistant

Самостоятельное локальное Android-приложение на Kotlin и Jetpack Compose для учёта личных тренировок. Интернет, внешние аккаунты и сервер не нужны. Данные хранятся на устройстве; импорт и резервное копирование выполняются по выбору пользователя через файлы.

## Возможности

- универсальная запись тренировки: дата, вид спорта и спортивный центр;
- отдельная статистика каждого вида спорта;
- редактирование и подтверждаемое удаление результатов из календаря и статистики; сохраняемые черновики и ошибки полей;
- футбол: счёт, личные голы и передачи, необязательные дистанция, число игроков в команде и длительность;
- скалолазание: несколько трасс за тренировку; трудность с французской шкалой `3a`–`9c`, болдер с Fontainebleau `1B`–`9A`, скорость с явным выбором эталонной 15 м / иной трассы; результат каждой попытки;
- общие фильтры периода/центра, включая архив; месяцы без тренировок, подробные спортивные агрегаты и история страницами по 20 записей;
- календарь результатов, планов и отмен; перенос и отмена одного события/всей серии, запись связанного результата из плана;
- редактируемый справочник спортивных центров, доступных видов спорта и архив без потери истории;
- импорт футбольной истории из CSV;
- локальный экспорт и повторный импорт резервной копии JSON;
- предпросмотр, выбор профиля и сопоставление центров; повторный импорт по UUID без слияния одинаковых реальных тренировок.

При первом запуске создаются только справочники и локальный профиль; демонстрационные тренировки используются исключительно в тестах и не попадают в пользовательскую статистику.

В установленном APK нет сетевых разрешений. Автоматический системный бэкап отключён; правила Android исключают данные из облачного бэкапа и автоматического переноса между устройствами. Для резервирования используйте ручной экспорт JSON перед удалением приложения или очисткой его данных.

Базовая таблица `trainings` не содержит специфичных для спорта полей. Футбольные данные лежат в `football_trainings`, скалолазные — в `climbing_trainings` и `climbing_routes`. Поэтому новый вид спорта добавляется отдельной дочерней сущностью, формой и расчётом статистики без изменения общих атрибутов календаря.

## Импорт футбольной истории из CSV

Приложение принимает UTF-8/UTF-8 BOM и Windows-1251, разделители `;` и `,`. Поддерживаемый заголовок:

```csv
user_id;training_date;sports_complex_id;team_goals_scored;team_goals_conceded;user_goals_scored;user_assists;distance_km
1;2025-12-14;2;5;3;2;1;7,35
1;2025-12-21;2;1;1;0;1;
```

`sports_complex_id` — номер из файла, не надёжный локальный ключ: перед применением CSV подтвердите существующий центр или создание исторического. Начальные номера `1` («Энергия Высоты»), `2` («Фабрика Футбола»), `3` («Арена на горе») относятся только к чистой установке. `user_id` — поле старого формата файла, не внешний аккаунт. При нескольких пользователях выберите один профиль или явно сохраните все отдельно; личная статистика не смешивается. Необязательные колонки `players_per_team` и `duration_minutes` также поддерживаются, как и отсутствие `distance_km`.

## Резервная копия

Экран «Данные» создаёт согласованный снимок JSON (`schemaVersion = 6`) через системный диалог Android. В копию входят UUID и даты создания, спортивные детали и метаданные шкал, все профили, центры, их виды спорта и состояние архива, история, серии, статусы, исключения серий и связи плана с результатом/серией, избранное и подтверждённые сопоставления.

После записи файл читается обратно и сравнивается; отмена диалога не отображает успех. JSON не зашифрован. Выбирайте локальное хранилище: облачные пункты системного диалога предоставляются сторонними приложениями. Широкие разрешения на хранилище не нужны.

Импорт JSON 1–6 и футбольного CSV сначала показывает предпросмотр, затем повторно проверяет выбор и применяет весь файл в транзакции. База не очищается; ошибка откатывает все изменения. Один UUID не вставляется повторно, конфликт требует подтверждения сохранения локальной записи. Две реальные одинаковые тренировки с разными UUID не сливаются. Старые файлы получают идентичность по точным байтам и позиции записи: изменённый файл считается новым источником, возможные совпадения показаны без автоматического удаления.

Операции ограничены 16 МиБ и 100000 объектов суммарно, выполняются в фоне и защищены от повторного запуска. Старые JSON не содержали владельцев, дат создания и связей плана с серией: отсутствующие сведения не угадываются. Реальная многолетняя история не предоставлена; произвольные выгрузки скалолазания не обещаются без образца. Подробности — в `docs/backup-format.md`.

## Сборка

Стабильные версии, проверенные по первичным источникам 7 октября 2026 года (подробности в отчёте этапа 2):

- Android Gradle Plugin `9.4.1`;
- Gradle `9.8.0`;
- встроенный в AGP Kotlin + Compose/Serialization plugins `2.4.20`, KSP `2.3.12`;
- Compose BOM `2026.09.00`;
- Room `2.8.5`;
- compile SDK `37.1`, target SDK `37`, min SDK `26`;
- Java source/target `17`; фактический JDK локального прогона указан в отчёте этапа.

```powershell
$env:JAVA_HOME='C:\Program Files\Android\Android Studio\jbr'
.\gradlew.bat verifyOfflinePolicy testDebugUnitTest lintDebug assembleDebug
.\gradlew.bat connectedDebugAndroidTest
```

Debug APK создаётся в `app/build/outputs/apk/debug/app-debug.apk`.

## Проверки

Unit-тесты покрывают парсинг CSV, обе кодировки, JSON round-trip, справочник сложностей и спортивные агрегаты. Инструментальные тесты на эмуляторе проверяют миграцию Room `1 → 2` и сохранение старых агрегированных данных скалолазания.

Этап 3 ввёл локальную идентичность, UUID и реестр спортивных модулей. Этап 4 вводит схему Room 4 с миграцией `3 → 4`, раздельные шкалы и максимумы успешно пройденных трасс; неоднозначная история сохраняется без сравнения категорий. Схемы 2, 3, 4, 5, 6 и 7 сохранены в `app/schemas`. Обычное сохранение и импорт используют общие проверки спортивных деталей; первые операции ждут транзакционной инициализации. Две одинаковые тренировки сохраняются вручную как разные записи. Этап 5 вводит Room 5 с миграцией `4 → 5` и JSON 4: обмен UUID, предварительный просмотр, безопасное объединение и сохранение связей. Этап 6 добавляет Room 6 / миграцию `5 → 6`, JSON 5, архивирование и проверку нормализованных дублей; исторические ссылки не удаляются. Этап 7 завершает CRUD результатов, saveable-черновики, числовую клавиатуру и ошибки полей; схема Room 6 и JSON 5 не меняются. Этап 8 вводит Room 7 / миграцию `6 → 7` и JSON 6: связанные результаты, отмены и переносы одного события, редактирование/отмена всей серии с сохранением исключений, наблюдение базы и смена текущей даты. Миграция только добавляет поля/индексы без изменения исторических связей. Этап 9 (приложение 1.8.0) добавляет общие фильтры и SQL-агрегаты, точные суммы/средние с числом учтённых значений, распределения скалолазания и постраничную историю; Room 7 и JSON 6 не меняются. Поддерживаются адаптеры JSON 1–5; старые обозначения и группировка трасс сохраняются. Диапазоны встроенного справочника не объявлены официальными мировыми пределами; источники и применимость описаны отдельно.

На этапе 1 добавлены инструментальные проверки офлайн-политики установленного APK и контрольного набора статистики/календаря. Актуальные числа тестов, результаты запуска и ограничения приведены в отчёте последнего завершённого этапа.

Сборка из пустого кэша требует загрузки инструментов и библиотек. После загрузки повторные сборки можно выполнять с `--offline`. Работа установленного приложения не требует сети.

`verifyOfflinePolicy` проверяет объединённые манифесты обеих сборок на отсутствие сетевых разрешений и отключение системного бэкапа. `.github/workflows/android.yml` запускает эту проверку, модульные тесты, Lint и сборки debug/release; действия закреплены полными SHA. `assembleRelease` пока создаёт неподписанный APK, без публикации. Все версии библиотек находятся в `gradle/libs.versions.toml`.
